<objective>
Update the Drizzle schema so that auth-owned tables (`user`, `session`, `account`, `verification`) are no longer managed by the app's migrations when Neon Auth is active — Neon Auth manages these tables in its own `neon_auth` schema. Remove cross-schema FK constraints from `board_api_keys.userId` and `cli_auth_challenges.approvedByUserId` so they store user IDs as plain strings compatible with `neon_auth.user.id`.

Purpose: AUTH-05 — the Drizzle schema strategy must align with `neon_auth`; removes the breaking FK constraint that would prevent Neon Auth user IDs from being used in referencing tables.
Output: Updated Drizzle schema files; exports remain intact for downstream consumers; FORK_DIFF.md updated.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Drizzle schema → Postgres | Schema defines table shape; removing FK constraints means the DB no longer enforces referential integrity at the constraint level |
| Application code → userId strings | User IDs from Neon Auth are trusted because they come from a validated session token; no DB-level FK enforcement |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-09 | Tampering | board_api_keys.userId without FK | mitigate | User ID in API keys is set at creation time from `req.actor.userId` (session-validated); an attacker cannot supply an arbitrary userId without a valid session — application-layer enforcement replaces DB constraint (ASVS L1 V4.1) |
| T-02-10 | Tampering | cli_auth_challenges.approvedByUserId without FK | mitigate | approvedByUserId is set from session at approval time; same reasoning as T-02-09 |
| T-02-11 | Information Disclosure | neon_auth schema cross-tenant reads | accept | The neon_auth schema is controlled by Neon Auth; app code only reads user ID from session, not from cross-schema table scans; no PII leakage risk from schema change |
| T-02-12 | Denial of Service | Orphaned API keys after user deletion | accept | Neon Auth manages user lifecycle; orphaned API keys become permanently invalid (next session check fails); acceptable for internal deployment |
</threat_model>
