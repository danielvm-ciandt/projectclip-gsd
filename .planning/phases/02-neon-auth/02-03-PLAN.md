**handleGoogleSignIn:**
```typescript
async function handleGoogleSignIn() {
  setIsLoading(true);
  setError(null);
  try {
    await authClient.signIn.social({ provider: "google", callbackURL: "/" });
    // After OAuth redirect returns, check domain:
    const session = await authClient.getSession();
    const email = session?.data?.user?.email ?? "";
    if (!email.endsWith("@ciandt.com")) {
      await authClient.signOut();
      setError("This instance only allows CI&T Google accounts. Use an @ciandt.com address or contact your administrator.");
      return;
    }
    // Redirect to ?next= or /
    const params = new URLSearchParams(window.location.search);
    window.location.href = params.get("next") ?? "/";
  } catch {
    setError("Sign-in failed. Try again, or contact your administrator if this keeps happening.");
  } finally {
    setIsLoading(false);
  }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → /api/auth/sign-in/social | OAuth initiation from SPA goes through the Express proxy to Neon Auth |
| OAuth provider → Neon Auth callback | Google OAuth redirect handled by Neon Auth managed service |
| Neon Auth → SPA session cookie | Session cookie set after successful OAuth; validated per plan 02-01 |
| SPA email domain check | Post-sign-in check that user email ends in @ciandt.com before allowing access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-13 | Spoofing | @ciandt.com domain check in Auth.tsx | mitigate | Domain check runs AFTER session is established — checks session.user.email from Neon Auth (server-authoritative); if email fails check, authClient.signOut() is called immediately (ASVS L1 V2.2) |
| T-02-14 | Spoofing | ?next= redirect after login | mitigate | `next` param is used for same-origin redirect only; validate that `next` starts with `/` before using — if it doesn't, redirect to `/` (open redirect prevention per ASVS L1 V5.1) |
| T-02-15 | Information Disclosure | Auth error messages | mitigate | Error messages per UI-SPEC contain only user-actionable text; no stack traces, internal URLs, or session tokens exposed in UI |
| T-02-16 | Spoofing | Email break-glass path | mitigate | Email/password sign-in flows through same Express proxy → Neon Auth REST API; server-side signup block (403 on POST /api/auth/sign-up/email from plan 02-01) is active regardless of UI state |
| T-02-17 | Elevation of Privilege | Session redirect when already signed in | accept | Redirecting an active session to / is standard behavior; no privilege escalation possible since session is already validated |
</threat_model>
